# L.o.S.A. — спецификация лобби, косметики и внешнего вида

Документ переводит продуктовые решения в требования, по которым можно реализовывать интерфейс и сервисы без привязки к незавершённой авторизации.

## 1. Главное решение по Java и Bedrock

Java и Bedrock — две самостоятельные игровые сети. Они не используют общий игровой серверный кластер и не обязаны поддерживать кроссплей. При этом пользовательский опыт должен быть максимально похожим: одинаковая логика навигации, сходные режимы, правила, оформление, сезонные события и единый стиль коммуникации.

Общие компоненты продукта:
- интерфейс лаунчера и его настройки;
- нейтральная стартовая зона/лобби лаунчера;
- каталог серверов с фильтрацией по платформе;
- концепция каталога косметики и идентификаторы предметов;
- будущая учётная запись L.o.S.A., друзья, права владения предметами и модерация.

Раздельные компоненты:
- Java- и Bedrock-игровые серверы, их конфигурация, мониторинг и обновление;
- клиентские компоненты косметики;
- платформенные профили сборок и способы запуска;
- тестовые матрицы, версии и ограничения совместимости.

## 2. Лобби лаунчера и выбор сборки

### До выбора сборки
Лобби является общей нейтральной частью лаунчера. Оно не должно заранее заставлять пользователя выбирать Java или Bedrock и не должно менять свой интерфейс в зависимости от случайного последнего выбора. В нём доступны:
- главная панель и новости;
- навигация к друзьям, серверному браузеру и будущему магазину;
- список пользовательских сборок и действие «Создать сборку»;
- общие настройки лаунчера и локального профиля.

### После выбора сборки
Каждая сборка обязана иметь явное поле платформы: `java` или `bedrock`. Платформа определяется при создании сборки и сохраняется в её метаданных. При выборе сборки лаунчер:
1. читает платформу сборки;
2. проверяет, доступен ли соответствующий способ запуска;
3. фильтрует серверы и режимы по платформе и версии;
4. подбирает соответствующий клиентский компонент косметики;
5. показывает только поддерживаемые действия.

Нельзя определять платформу по названию сборки, тексту версии или произвольному имени папки. Нельзя показывать Java-сервер как совместимый с Bedrock без отдельно проверенной поддержки.

### Состояния интерфейса
- Сборка не выбрана: нейтральное лобби и предложение создать/выбрать сборку.
- Сборка Java выбрана: доступны Java-версии, Java-серверы и Java-мод косметики.
- Сборка Bedrock выбрана: доступны поддерживаемые Bedrock-платформы/версии, Bedrock-серверы и Bedrock-косметика.
- Платформа не поддерживается: показать причину и способ продолжить, не выдавая ложную кнопку запуска.
- Сборка повреждена или неполна: предложить автоматическое восстановление/проверку, а не ручное скачивание библиотек.

## 3. Сборки и UX создания

Создание сборки должно быть коротким и понятным:
1. название и необязательный логотип;
2. выбор платформы (Java или Bedrock);
3. версия/канал, доступные для выбранной платформы;
4. необязательные моды/пакеты и настройки;
5. одна основная кнопка «Создать сборку».

После подтверждения лаунчер сам выполняет необходимые загрузки, проверку файлов и подготовку запуска. Не показывать обычному пользователю отдельные технические действия «Скачать библиотеки», «Скачать assets», «Скачать natives». Если задача требует загрузки, интерфейс показывает единый прогресс с понятными этапами и кнопкой отмены, где это безопасно.

Сборки должны иметь стабильный уникальный ID, имя, логотип, платформу, версию, список установленных компонентов и время последнего запуска. Переименование не должно менять ID или ломать сохранённые данные. Пользователь может создать несколько сборок, переключаться между ними, редактировать и удалять их с подтверждением.

## 4. Два мода косметики

Требуются две самостоятельные реализации:
- **L.o.S.A. Cosmetics для Java** — мод, использующий поддерживаемый модлоадер и API выбранных версий Java Edition.
- **L.o.S.A. Cosmetics для Bedrock** — отдельная реализация на поддерживаемых Bedrock-механизмах (resource pack, behavior pack и/или серверная выдача/отображение, выбранные после прототипа).

Это два разных проекта/артефакта, а не один мод с переключателем. У них разные API, формат ресурсов, жизненный цикл, установка и ограничения. Нельзя считать Java-мод совместимым с Bedrock.

### Общая модель предмета
Каждый предмет получает стабильный идентификатор и общие метаданные:
- `item_id` — неизменяемый ID;
- `display_name` и локализованные описания;
- `category` (например, cape, hat, aura, emote);
- `rarity` и сезон/коллекция;
- `ownership_policy` и источник выдачи;
- `java_asset_version` и `bedrock_asset_version`;
- правила доступности по версии и режиму.

Каталог и владение предметом хранятся на стороне сервиса L.o.S.A. Клиентский мод не является источником истины: он получает подтверждённый список разрешённых предметов и только отображает их. Клиент не может самостоятельно начислить валюту, купить предмет или назначить роль.

### Установка и обновление
Лаунчер после выбора сборки определяет платформу и автоматически подбирает нужный артефакт косметики. Он проверяет совместимость с версией игры и модлоадером/Bedrock-пакетом, загружает из доверенного источника, проверяет контрольную сумму и устанавливает в область выбранной сборки. Обновление должно быть атомарным: при ошибке остаётся предыдущая рабочая версия. Для отключения косметики нужен простой переключатель.

Версии двух реализаций могут выпускаться независимо, но каталог предметов должен сообщать, какие платформы и версии поддерживает каждый предмет. Если предмет недоступен на одной платформе, магазин обязан явно показать это до покупки. Для общей покупки заранее определить политику: предмет открывает все поддерживаемые варианты, если это задумано для данного товара; иначе платформа-специфичность показывается до оплаты.

### Безопасность и честная игра
- Косметика не даёт урона, скорости, ресурсов, скрытности или иных игровых преимуществ.
- Сервер проверяет право владения предметом; локальный конфиг не может открыть платный контент.
- Встроенные URL, исполняемые файлы и обновления подписываются/проверяются; никаких произвольных исполняемых загрузок из каталога.
- Нужны журнал выдачи, отзыв предмета, возврат и защита от повторной транзакции.
- Косметика должна иметь безопасный режим отключения и не блокировать вход на сервер при временной недоступности сервиса.

## 5. Внешний вид лаунчера

Внешний вид лаунчера отделён от оформления конкретной сборки. Изменение темы не меняет логотип/название сборки и не затрагивает игровые настройки.

Минимальный набор локальных настроек:
- тема: системная, тёмная, светлая;
- акцент: несколько заранее проверенных цветов;
- фон: стандартный или пользовательское изображение с ограничением формата/размера;
- плотность: обычная/компактная;
- анимации: стандартные/уменьшенные/выключенные;
- масштаб интерфейса;
- кнопка «Сбросить внешний вид».

Требования:
- настройки сохраняются локально и доступны без регистрации;
- изменения применяются сразу и переживают перезапуск;
- текст и кнопки сохраняют достаточный контраст;
- фон не перекрывает читаемость и не загружается как исполняемый контент;
- пользователь может вернуть стандартный вид одной кнопкой.

## 6. Экраны будущего магазина

Каталог:
- категории и фильтры;
- карточка предмета с превью, описанием, редкостью и совместимостью Java/Bedrock;
- понятное состояние «уже есть», «недоступно для этой платформы», «скоро»;
- цена и условия до подтверждения покупки.

Карточка предмета:
- просмотр доступных платформенных вариантов;
- список поддерживаемых версий;
- предупреждение, если для отображения нужен компонент, который ещё не установлен;
- никаких фиктивных кнопок покупки до появления backend и платёжной логики.

Инвентарь:
- принадлежащие игроку предметы;
- избранное/активный предмет;
- фильтр по платформе;
- история получения.

## 7. Что можно реализовывать без backend прямо сейчас

- локальные темы, акцент, фон, плотность и масштаб;
- структуру экранов лобби, сборок, друзей, серверного браузера и магазина;
- модель метаданных сборки с явной платформой;
- фильтрацию серверных карточек по платформе на локальных тестовых данных;
- интерфейс каталога косметики с честными статусами «демо»/«скоро»;
- локальные тестовые наборы предметов для разработки двух модов;
- проверку совместимости и обновления модов на тестовых артефактах.

Нельзя без backend объявлять работающими аккаунты, друзей между пользователями, покупки, баланс, облачный инвентарь, права владения, глобальную модерацию или сетевые приглашения.

## 8. Очерёдность

1. Стабилизировать текущий запуск Java и не допустить регрессий.
2. Довести модель сборок до явного поля платформы, не ломая существующие Java-сборки.
3. Сделать нейтральное лобби и базовые локальные настройки внешнего вида.
4. Подготовить отдельные прототипы Java- и Bedrock-косметики и выбрать совместимые технические основы.
5. Подготовить серверный MVP отдельно для каждой платформы; начать с одного режима на платформу.
6. После появления собственной авторизации и backend подключать друзей, синхронизацию инвентаря и магазин.

## 9. Приёмочные проверки

- До выбора сборки лобби не меняет платформу и не показывает редакционно-специфичные игровые действия.
- Выбор Java-сборки включает только Java-путь; выбор Bedrock-сборки — только Bedrock-путь.
- Неподдерживаемая комбинация версии/мода/сервера блокируется с понятным объяснением.
- Две реализации косметики собираются и тестируются отдельно.
- Общий ID предмета связывает платформенные варианты без требования одинаковых файлов.
- Тема и параметры внешнего вида сохраняются после перезапуска.
- Отсутствие backend не маскируется фальшивыми данными.
- Создание и запуск существующих Java-сборок остаются рабочими.
